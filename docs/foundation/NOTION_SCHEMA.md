# Notion 資料庫交互邏輯

這份文件說明 Bot 如何讀寫 KariKari 的 Notion 資料層。  
目前 schema 仍以 KariKari 為第一測試站；未來平展化時，這些欄位名稱應抽到 schema mapping。

## 核心原則

- Notion 是營運資料來源。
- Discord 是操作入口。
- `Availability Slots` 只代表可配合時間，不代表正式行程。
- 正式安排以 `Tasks` / `Projects` 為主。
- 重要操作寫入 `Audit Log`。

## 佈告欄／留言板／使用回饋

用途：營運公告、待討論事項、會議摘要與使用回饋的集中紀錄。

目前 Bot 會讀取 KariKari Testing 的布告欄，並同步到 Discord 公告區：

| 欄位 | Bot 用途 |
|---|---|
| `Name` | Discord 公告標題 |
| `類別` | 顯示公告、待討論、會議摘要或使用回饋 |
| `狀態` | 顯示未處理、處理中或已結案 |
| `Date` | 顯示事項日期 |
| `人員` | 顯示相關人員 |
| `📌 置頂` | 在 Discord 標題前顯示置頂標記 |

同步規則：

- Notion 是正式資料來源，Discord 是通知與查看入口。
- 新增 Notion 項目會發到 Discord；內容或狀態變更會更新原訊息。
- 同一筆 Notion 項目不會重複發布；Bot 會將對應訊息 ID 保存在本機 `.state/bulletin_sync.json`。
- Discord 公告**不含 Notion 頁面連結**（公告區藝人看得到）；公告內容要在 Notion 布告欄的標題、類別、狀態、人員欄位寫齊，藝人只看得到這些。
- 使用者按「回報／留言」或直接回覆 Discord 公告時，Bot 會在同一個布告欄資料庫建立 `🙋 使用回饋`，狀態預設為 `未處理`。
- 回饋內容寫在新 Notion 頁面的內容區，並包含 Discord 使用者、原公告與 Discord 回覆連結。
- 可使用 `/布告欄同步` 立即同步，背景同步預設每 5 分鐘執行。

## Artists｜藝人資料

用途：身份來源與可排課藝人清單。

Bot 讀取：

| 欄位 | 用途 |
|---|---|
| `藝人名稱` | Discord 顯示名稱 |
| `Discord User ID` | 將 Discord 使用者對應到 Notion 藝人 |
| `合約狀態` | 判斷是否可排課 |
| `Google Drive 資料夾` | 藝人專區連結，作業檔案自動歸檔基底 |

可排課條件：

- 有 `Discord User ID`
- `合約狀態` 為 `已簽約` 或 `洽談中`；`未簽` / `暫停` / `封存` 不可使用藝人功能

相關功能：

- `/管理可配合時間`
- `/我的任務`
- `/時間資訊蒐集`
- `/從時間池建立任務`

## 課程與會議記錄

用途：保存公司會議、課程會議與各類對外會議紀錄，作為 Discord 小律（會議秘書）的查詢來源。

Bot／LLM 可使用的安全條件：

- `參與藝人` 直接關聯該藝人，或由 Tasks 的 `課程與會議記錄`／`關聯專案` 反向追溯到該藝人。
- `會議類型` 不在 `qa_hidden_meeting_types` 這組排除清單內（KariKari 目前排除 `課程`、`課程會議`、`公司例會`、`管理層會議`）。新增其他會議類型時預設就會開放查詢，不需要改設定。排除由 bot 讀回資料後自己做，不放進 Notion 篩選（篩選帶到不存在的選項會整個查詢失敗；2026-10-18 正式環境已沒有 `公司例會`、`管理層會議`，小律因此查詢失敗過）。
- `藝人可見` 已勾選。

人工維護規則：

1. 會議結束後手動整理內容。
2. 補上 `參與藝人`、`參與老師`、`關聯專案`；若由任務產生，再於 Task 補上 `課程與會議記錄`。
3. 確認頁面沒有財務、合約、人事等不應提供給藝人的內容。
4. 確認後才勾選 `藝人可見`。

`藝人可見` 預設為未勾選；未勾選的紀錄永遠不提供給藝人查詢。`會議類型` 屬於排除清單的紀錄，即使勾選 `藝人可見` 也一律不提供。

小律查詢時會讀取頁面內容與 `會議摘要`，不會修改課程與會議紀錄。

### 藝人端一律不給 Notion 連結（2026-09-18）

這是**全系統規則**，不只小律：`藝人可見` 之類的逐頁勾選管不到 Notion 頁面上方的導覽列——藝人拿到任何一個頁面網址，就能往上翻到整個資料庫。一筆任務的網址翻上去就是所有藝人的 Tasks。

因此網址不出現在藝人看得到的任何輸出。已移除的入口：任務通知／未確認提醒的「查看任務內容」按鈕、按「收到任務」後的回覆、審核結果與批改檔 DM 的「查看 Notion 任務」、公告區的公開公告與布告欄同步、小律的附件索引／月份總覽／回答來源。

控方與老師的頻道不受限（`/審核提交` 詳情、營運內部通知仍保留連結）。守門測試在 `tests/test_artist_no_notion_links.py`。

網址也不進 LLM 的 context（`services/course_qa.py` 的 `_record_text`），否則模型會照抄進回答；回答送出前另外再過濾一次 Notion 網域當保險。會議內容裡提到的其他連結（參考影片、共用雲端）不受影響，照常提供給藝人。

### 附件與檔案索引

- 會議頁中的 Notion `file` block 會被整理成檔案索引，顯示檔名與來源頁面。
- Bot 不會在第一次查詢時把所有附件文字直接併入正文。
- 藝人先從 Discord 看到自己有權限的檔案清單，再指定頁面或檔名；只有被指定的附件才會納入該次 LLM 檢索。
- PDF、DOCX、PPTX、XLSX 與常見純文字檔會嘗試抽取文字；檔案索引與頁面正文仍保持分開。
- 檔案讀取只在 `藝人可見`、藝人關聯與會議類型排除清單都通過後發生，不會跨藝人共享。
- 小律只讀取資料，不會修改課程與會議記錄或附件。
- `未簽`、`暫停`、`封存` 藝人不可使用小律。
- AI 使用量只保存在本機狀態檔中的日期、識別鍵與 token 數，不保存問題全文。
- 個人與全系統每日 token 護欄可透過環境變數設定；KariKari 目前皆為 `0`（不限額），LLM 供應商帳戶限制仍適用。
- 藝人按 `回報問題` 時，才會把他主動填寫的回報內容寫入布告欄 `🙋 使用回饋`；不會附帶原始問題全文。
- 小律每次提問重新同步 Notion；同步失敗才使用該藝人上次成功的快取，不跨藝人共用。
- 檢索意圖會先限制在明確的月份、主題、老師、附件或總覽範圍；模糊問題不會把任意紀錄交給 LLM。
- LLM 上下文最多 16,000 字並以完整紀錄裁切，避免來源被截斷；逾時、網路錯誤或服務端 5xx 只重試一次。
- 使用 OpenAI `gpt-5.6-luna`；正式內容空白或格式不完整時不寫入假答案。LongCat 已禁止使用，相關設定會在送出請求前被拒絕。

## Availability Slots｜可用時段

用途：保存藝人回填的可配合時間。

Bot 寫入：

| 欄位 | 用途 |
|---|---|
| `可用時段名稱` | 人類可讀的時段名稱 |
| `填寫藝人` | 關聯 Artists |
| `填寫人名稱` | 顯示用 |
| `身份` | 目前為藝人 |
| `來源` | Discord |
| `可用開始時間` | 時段開始 |
| `可用結束時間` | 時段結束 |
| `提交時間` | 藝人送出時間 |
| `是否逾期提交` | 是否超過收集截止 |
| `備註` | 收集月份、收集性質、藝人備註、既有任務提醒 |

備註慣例：

- `收集月份：YYYY-MM`
- `收集性質：月度可配合時段`
- `藝人備註：...`
- `既有任務提醒：...`

整理規則：

- 同一藝人、同一開始、同一結束不重複新增。
- 同一天重疊或被較寬時段涵蓋時，整理流程會合併或封存冗餘資料。
- 刪除時會 archive Notion page，不硬刪。

相關功能：

- `/管理可配合時間`
- `/從時間池建立任務`

## Tasks｜任務總表

用途：正式安排、營運任務、藝人任務查詢與提醒來源。

Bot 讀取：

| 欄位 | 用途 |
|---|---|
| `任務名稱` | 顯示與提醒 |
| `任務狀態` | 判斷是否未結案 |
| `任務類型` | 判斷是否硬性佔用 |
| `課程類別` | 課程時間&作業繳交任務的具體課程，例如歌唱課、編曲課 |
| `負責老師` | Relation 到 `People｜人員資料`，只選身份類型為老師的人員。課程培訓類任務結束後，Bot 會私訊負責老師到論壇發布（M5-01）；老師沒有 Discord User ID 時改發控方頻道 |
| `課程與會議記錄` | Relation 到課程與會議記錄，供小律反向判斷藝人可見範圍 |
| `審核人員` | Relation 到 `🧑🏻‍🏫 成員・老師・合作方`；只選 `身份類型=公司成員` 的人，可空白 |
| `開始日` | 正式安排開始 |
| `截止日` | 正式安排結束；一般非提交任務可作為任務截止 |
| `關聯藝人` | 任務的藝人執行者（Relation → Artists）：可收任務、確認、提交，並影響任務狀態 |
| `相關同仁` | 任務的老師／公司同仁（Relation → People）：收派發與截止前／逾期純通知，無按鈕、不影響任務狀態 |
| `關聯專案` | 若 Task 未直接關聯藝人，透過 Project 找藝人 |
| `Discord 顯示` | 控制是否出現在藝人 `/我的任務` |
| `是否開放提交` | 控制任務是否出現在 `/我的任務` → `提交任務` 清單 |
| `提交方式` | **已刪除**（M4-03）：程式不再讀取，Notion 欄位 2026-10-13 確認已移除，交件一律上傳公司 Drive |
| `提交期限` | 第一次提交期限；由控方直接在 Notion 設定，不覆蓋正式行程的 `截止日` |
| `最新提交 URL` | 提交後由 Bot 回寫，指向最新一筆 `Submissions & File Index` 頁面 |
| `提醒規則` | 任務提醒使用。與 `DEFAULT_REMINDER_RULES`（預設 `5 天前,3 天前`）**取聯集**，勾選只能往上加。選項只有 3 天前／1 天前／當天／逾期；「5 天前」刻意不加回（2026-10-11 決定，預設已含 D-5） |
| `重送通知` | checkbox，2026-10-11 新增（2026-10-13 確認已在正式 Notion 建立）。勾了＝下一輪批次重送這筆任務的通知，Bot 重送前自動取消勾選。欄位不存在時功能不啟動 |
| `提前交件` | checkbox，2026-09-20 新增。勾了＝交件死線提前：`提交期限` 有填用它，沒填＝`截止日 − APPROVAL_LEAD_DAYS`（預設 5）。逾期以這條死線判定。上課等沒勾提前交件的任務不勾 |
| `提醒確認(From 藝人)` | text，2026-09-20 新增（括號半形、From 後一個空格，名稱要完全一致）。Bot 逐行追加 `階段｜MM/DD HH:MM｜藝人名`；送出時也記一行 `…｜已發送給 N 人`，讓控方分得出「還沒發」和「發了沒人按」。`/任務通知重送` 會清空。欄位不存在時 Bot 自動降級，只留 Audit Log |
| `Discord 通知時間` | Bot 首次派發任務通知的時間 |
| `Discord 收到時間` | 藝人按「收到任務」後由 Bot 回寫的時間 |
| `修改期限` | 審核人選擇 1～7 天後由 Bot 寫入；Notion 也可人工調整 |

`Discord 顯示` 的用途：

- 有勾：藝人可在 `/我的任務` 看到。
- 未勾：即使任務關聯藝人，也不顯示給藝人。
- 用來保護控方內部任務、尚未確認安排、管理層備註。

任務派發確認：

- `關聯藝人` 與 `相關同仁` 合稱「任務相關對象」。Notion relation 無法同時指向 Artists 與 People，因此保留兩欄，而非把 `關聯藝人` 改名為易誤解的「相關人士」。
- 新任務勾選 `Discord 顯示` 並關聯藝人後，Bot 會私訊藝人並附「收到任務」按鈕。
- `PUBLIC_TASK_TYPES` 設定中的任務類型（預設：通告、演出）會在藝人私訊成功後額外發到公告區；其他類型只私訊藝人。
  設定值必須是 `任務類型` 既有的選項，填不存在的值不會報錯但永遠不命中。
- 藝人也可以按「有問題／無法配合」並填寫原因；由於定稿 Tasks schema 沒有 `備註` 欄位，Bot 會把標記過的原因追加到該筆 Task 內頁的「藝人回覆」區塊，不覆蓋 `任務說明`，並通知營運內部通知頻道。同時任務會退回 `尚未開始`、取消 `Discord 顯示`，並清空 `Discord 通知時間`／`Discord 收到時間`。控方修改後重新勾選 `Discord 顯示` 即可重新派發。
- 「收到任務」是逐筆確認，不代表同一批其他任務也已收到；每筆任務的 `Discord 收到時間` 分開判斷。
- Bot 每 12 小時固定掃描一次，按藝人彙整當下所有未確認任務，再次私訊摘要與逐筆原始通知。
- 每則帶按鈕的通知都記下訊息編號（`.state/task_notification_log.json`，保留 45 天）；藝人按「收到任務」時，同任務之前發給他的通知全部改成「✅ 已收到」並拿掉按鈕（M3-23）。
- `是否開放提交` 是課程與作業的第二階段開關：課程剛建立時可先不勾選；老師／控方補齊作業要求、審核人員與 `提交期限` 後勾選，背景輪詢會發送一次課後作業通知。通知狀態保存於 Bot state，並寫入 `Audit Log`，不會重複發送。
- 首次提交階段以 `提交期限` 提醒；舊資料未填此欄位時才相容沿用 `截止日`。
- **提前交件任務的死線**（2026-09-20）：`提前交件` 勾選時，追蹤的期限優先序為 `提交期限` → `截止日 − APPROVAL_LEAD_DAYS`；藝人端顯示「交件 M/D」而非「截止」，逾期也以交件日判定。一個任務進行到底，不拆「交件」「發布」兩筆，因此發布日當天不會再有提醒（已知取捨）。
- **截止前提醒帶「收到通知」按鈕**：5 天前／3 天前／1 天前／當天的提醒各附一顆，逾期沒有。已發過的階段寫在 `.state/`，重啟不重發。藝人按了寫入 `提醒確認(From 藝人)`；Bot 送出時先寫一行「已發送給 N 人」。`待審核` 狀態不再發截止前提醒（東西已交，球在公司）。
- 任務進入 `需修改` 後，首次 `提交期限` 停止生效，只使用 Discord 審核時產生的 `修改期限`。
- 藝人重新提交後狀態改為 `待審核`，Bot 清除目前的 `修改期限`；歷史提交與審核仍保留在 Submissions 與 Audit Log。
- 課後作業通知的輪詢間隔由 `REMINDER_INTERVAL_MINUTES` 控制；測試可設 `0.5`（30 秒），正式建議 `10`。
- 藝人按下後，`任務狀態` 由 `尚未開始`／`待提交` 更新為 `進行中`，並寫入 `Discord 收到時間`。
- 若兩個 Discord 欄位尚未建立，收到時間至少會寫入 Audit Log；正式環境建議建立欄位以完整追蹤。
- Bot 第一次啟用通知時會先建立既有任務基準，不會一次通知所有歷史任務。
- 初次派送判斷以 `Discord 通知時間` 為準；Bot 啟動前已存在、但該欄位為空且仍是未結案狀態的任務也會補發。
- 背景輪詢會清理「未勾 Discord 顯示但仍殘留通知時間」的任務，避免控方重新開啟顯示時被舊派發紀錄擋住。
- 通知流程納入：`尚未開始`、`進行中`、`待提交`、`待審核`、`需修改`、`已逾期`、狀態空白；排除 `已完成`、`已完成發文`、`已取消`、`已封存`。`已取消` 即將停用（正式資料已無此狀態），之後統一用 `已封存`。
- 若找不到有效收件人，Bot 會通知控方，不會把任務標記為已通知。
- 控方可在任務頻道使用 `/任務通知重送` 清除兩個通知時間欄位，要求重新派發。

排程影響：

- 硬性佔用類型：`HARD_BLOCK_TASK_TYPES`（預設 `錄音`、`演出`、`會議溝通`），以及有 `課程類別` 的 `課程時間&作業繳交`
- 只有硬性類型且 `開始日` / `截止日` 都有明確時間，才會切掉藝人可配合時段。
- 只有日期、只有截止、或非硬性類型，只做提醒，不封鎖整天。

相關功能：

- `/我的任務`
- `/任務總覽`
- `/管理可配合時間`
- `/從時間池建立任務`
- 任務提醒 loop


## Submissions & File Index｜提交與檔案索引

用途：每一次作業／作品提交的紀錄與檔案索引。`/我的任務` → `提交任務` 寫入。

Bot 寫入：

| 欄位 | 用途 |
|---|---|
| `提交名稱` | 藝人｜任務｜時間 |
| `提交藝人` / `關聯任務` | relation 對回 Artists / Tasks |
| `提交來源` | Discord |
| `提交類型` | 一律寫 `檔案`（2026-10-11 起只有上傳一種交法；舊資料可能有 Drive 連結／文字／混合） |
| `檔案類型` | 依任務類型自動對應；`課程時間&作業繳交` 寫入 `課程作業`，其他類型照既有對應，沒列到的寫 `其他` |
| `Drive URL` | Bot 歸檔後的公司 Drive 連結 |
| `備註` | 舊的純文字提交內容（新提交不再使用） |
| `Drive File ID` / `原始檔名` / `檔案大小 MB` | Discord 檔案自動歸檔時回寫 |
| `提交時間` / `是否最新版` / `審核狀態`(待審核) / `權限等級`(藝人本人) | 狀態欄位。`權限等級` 只是標記，系統不依它做任何過濾（2026-10-11 決定不做權限區分） |
| `審核回饋` | 老師或控方給藝人的文字回饋 |
| `審核者` | Discord 審核者或 Notion 手動審核者 |
| `審核來源` | `Discord` / `Notion`，用來判斷通知來源 |
| `審核通知時間` | Bot 成功通知藝人的時間，避免重複通知 |

審核功能必備欄位：

- `/審核提交` 會寫入 `審核回饋`、`審核者`、`審核來源`、`審核通知時間`。
- 提交進入 `待審核` 時，Bot 不設定固定審核期限；提交滿 24 小時仍未審核，就列入每天 10:00 的每日催辦，私訊 Tasks `審核人員`，沒填或聯絡不到就發到控方頻道。
- `需修改`／`退回` 時，審核人於 Discord 輸入 1～7 天，Bot 寫入 `修改期限`；停在 `需修改` 期間每天 10:00 催藝人，修改期限一過通知控方一次。
- 若 Discord 顯示「審核寫入 Notion 失敗」，且提示確認這四個欄位，代表 `Submissions & File Index` 的 schema 尚未補齊。
- 欄位類型建議：
  - `審核回饋`：rich text
  - `審核者`：rich text
  - `審核來源`：select，選項至少包含 `Discord`、`Notion`
  - `審核通知時間`：date

重交規則：同任務舊提交自動取消 `是否最新版`——查最新版只要 filter `是否最新版=true`。

### 交件方式與檔案實際存放位置

- 交件只有一種方式：上傳到 Bot 建立的公司 Drive 資料夾（`Tasks.提交方式` 已停用）。
- 藝人檔案由 Bot 建立公司 Google Drive 指定資料夾並驗證；不接收 Discord 作業附件，也不提供私人 Drive 連結 fallback。
  隱私隔離：每個藝人專區只分享給該藝人本人（結構見下方「檔案路徑」）。
- `Artists.Google Drive 資料夾` 存專區連結，Bot 自動 find-or-create 子資料夾。
- 單一藝人任務首次提交時，Bot 會將任務資料夾連結自動回寫至 `Google Drive Folder`；有值則優先歸該資料夾。多人任務因每位藝人各有專區，連結會以藝人名稱標示後寫入 Task 內頁的「Drive 資料夾索引」；本次提交的資料夾連結保留在 Submission 的 `Drive URL`。
- Drive 顯示檔名自動加前綴：藝人提交檔案為 `{藝人名稱}_{任務名稱}_{原檔名}`，老師批改檔為 `老師回饋_{提交名稱}_{原檔名}`。
- 檔案路徑（2026-10-18 上線，取代舊的 `任務類型／YYYY-MM` 結構）： `藝人專區／專案名稱／YYYY.MM.DD_任務名稱／任務名稱_YYYY.MM.DD_ver.N`，專案名稱讀 Tasks `關聯專案` → Projects `專案名稱`，沒掛專案用 `未分專案`；`檔案類型` 改為任務類型 → 專案類型 → 其他。詳見 [SUBMISSION_FLOW.md](../operations/SUBMISSION_FLOW.md)「資料夾結構」與規則頁 M4-07、M4-16。
- 任務沒有截止日時，資料夾名稱的建立日期讀取 Notion page 的 `created_time`。
- 同一次 Discord 提交可包含多個檔案；Notion 建立一筆提交紀錄，`Drive URL` 指向本次資料夾，`原始檔名` 與 `Drive File ID` 保存檔案清單。
- 回寫 `Drive URL`＋`Drive File ID`＋`原始檔名`＋`檔案大小 MB`；其中 `原始檔名` 保留使用者上傳時的檔名。
- 大檔一樣直接上傳到 Bot 建立的資料夾，不經 Discord；老師批改檔案或連結會併入 `審核回饋`。
- 路徑邏輯在 `services/drive_archive.py`；Drive API 操作在 `services/drive_api.py`。
- 藝人檔案不做 Discord 10MB 分流，全部走 Google Drive；老師批改附件仍是獨立審核流程。
- 大型 Stem、DAW 專案、影片、大型音檔也一樣上傳到公司資料夾，不接受藝人自己的雲端連結。
- **P2**：冷資料轉 NAS，`NAS 路徑` 欄位已預留。

完整規則見 [SUBMISSION_FLOW.md](../operations/SUBMISSION_FLOW.md)。

### 審核流

- Discord `/審核提交` 會讀取最新版 `待審核` 提交。
- 控方選 `通過`、`需修改` 或 `退回`，可填 `審核回饋`。
- Bot 更新 Submissions 審核欄位，並同步更新 Tasks：
  - `通過` → Task `已完成`
  - `需修改` / `退回` → Task `需修改`
- Bot DM 藝人審核結果與回饋。
- Notion 端手動審核也支援：若 `審核狀態` 是結果值，且有 `審核回饋`、`審核者` 或 `審核來源` 任一欄，背景 loop 會通知藝人並回寫 `審核通知時間`。
## Projects｜專案

用途：上層歸屬與提醒來源。

Bot 讀取：

| 欄位 | 用途 |
|---|---|
| `專案名稱` | 提醒文字 |
| `專案狀態` | 判斷是否有效 |
| `關聯藝人` | Task 可透過 Project 找到藝人 |
| `開始日` | 營運提醒 |
| `截止日` | 營運提醒 |

排程影響：

- Project 日期只做提醒，不直接封鎖藝人時間。
- 若 Task 沒有直接關聯藝人，但有關聯 Project，Bot 會用 Project 的 `關聯藝人` 判斷 Task 屬於誰。

相關功能：

- `/管理可配合時間`
- `/從時間池建立任務`
- 正式安排衝突 / 提醒判斷

## 課程安排的單一來源

課程不再拆成獨立資料庫。`Tasks` 是課程與作業的唯一管理頁面：

```text
Project：課程培訓
└── Task：任務類型＝課程時間&作業繳交
    ├── 課程類別、負責老師、課程與會議記錄
    ├── 關聯藝人、開始日、截止日
    └── 作業提交與審核
```

`/從時間池建立任務` 選擇課程後，Bot 會選擇進行中的課程培訓 Project、老師與課程類別，直接建立一筆 Task；共同候選時段寫在任務內頁的 `任務說明` 區塊，正式時間由營運直接在 Task 填寫。錄音／通告／其他會先讀取 Tasks 的 `任務類型` schema 供控方選擇，再建立 `Discord 顯示=false` 的 Task 草稿；Bot 回覆會附上該筆 Notion Task 連結。確認內容後勾選 `Discord 顯示=true`，由背景通知流程自動通知藝人。

`Schedule Requests` 與 `Course Sessions` 已移出目前主流程並移至垃圾桶；其關聯欄位也已從 `Tasks` 與 `Availability Slots` 移除。歷史資料若需查閱，應從 Notion 垃圾桶恢復，不再由 Bot 讀寫。

## Audit Log｜操作紀錄

用途：追蹤 Bot 和使用者的重要操作。

Bot 寫入：

- Bot 啟動與 Notion smoke test
- 建立月度時間收集
- 藝人提交 / 刪除時間
- 時間池整理
- 建立課程與作業 Task
- 錯誤事件

原則：

- Audit Log 寫入失敗不阻斷主要流程。
- 重要資料異動都應留下可回溯紀錄。
